## Context

GitLab package-backed Release links in a private project require authentication.
The publication adapter already delegates JSON API reads to authenticated
`glab api`, but delegates asset bytes to anonymous `curl`; the same immutable
asset therefore succeeds in the publishing job and returns HTTP 401 to the
independent verifier.

## Goals / Non-Goals

**Goals:**

- Use one GitLab authentication owner for JSON and byte API reads.
- Preserve the exact Release link as the object being fetched.
- Preserve digest calculation and cross-Forge equality unchanged.

**Non-Goals:**

- Inject tokens, headers, credential helpers, or user-specific paths.
- Add fallback transports or make private packages public.
- Change GitHub verification, installation, runtime, or provider behavior.

## Decisions

1. Resolve `glab` through the existing hosted-transport executable boundary and
   invoke `glab api --method GET <release-link>`. `glab` already owns GitLab API
   host selection and credential storage, accepts absolute GitLab API URLs, and
   keeps secrets outside arguments generated by the product.
2. Do not add an anonymous-first fallback. Private and public projects use the
   same authenticated read, which keeps one deterministic transport and avoids
   duplicate requests or accidental credential-policy drift.
3. Assert the complete child command in the focused adapter test. The contract
   is not merely that bytes arrive, but that the GitLab authority plane owns the
   read instead of anonymous HTTP.

## Risks / Trade-offs

- A caller without a working `glab` login cannot verify hosted GitLab evidence
  -> retain the existing fail-closed publication error and documented explicit
  authentication boundary.
- Absolute asset URLs could target a different host -> `glab api` remains the
  GitLab transport authority and refuses unsupported host/auth contexts rather
  than leaking credentials through a generic HTTP client.

## Migration Plan

Land the focused repair with the full repository gates, advance to a new patch
release, verify both new provider-native releases and their assets, then install
only from the new signed release. Rollback before publication is a commit
revert; published tags and Releases remain immutable.
