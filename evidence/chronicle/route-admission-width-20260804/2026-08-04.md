# route-admission-width — 2026-08-04

- 2026-08-04: Root cause of the reported `Post
  "http://127.0.0.1:8792/dmxapi/v1/responses": context deadline exceeded`,
  measured on the live 2.0.9 listener rather than inferred. Every
  `responses_slot_acquired` line for the dmxapi route reported `active=1/8`: the
  process-wide bound was never the binding one. Individual route holds ran 23 to
  69 seconds, and request 38 waited 115 seconds between `request_sanitized` and
  `responses_slot_acquired` — it was queued behind other dmxapi turns the whole
  time, with seven of eight process slots idle. The listener reported 0
  queue-timeout denials, 0 rate limits, and 0 stream failures over the same
  window, so the defect was invisible to every counter the proxy keeps and
  visible only as latency to a client carrying its own deadline. Per-route
  admission at one had serialized a healthy route.
- 2026-08-04: The asymmetry that made this possible. Of the bounds that gate a
  Responses exchange, `RESPONSES_QUEUE_TIMEOUT`, `RESPONSES_MAX_CONCURRENCY`,
  and the upstream deadlines are all validated runtime settings projected into
  the supervised unit; `RESPONSES_MAX_PER_ROUTE` alone was a source constant
  (`runtime/admission.py:18`, `= 1`). It was therefore the one admission bound
  no operator could reach without a release. Widening the constant would have
  fixed today's latency and preserved that asymmetry, so the change makes it a
  setting first and widens the default second.
- 2026-08-04: The value was derived, not picked. Single-flight was originally
  adopted to protect a rate-limiting UCloud upstream; the owner reports that
  upstream no longer rate-limits, which removes serialization as a requirement
  but not *fairness* — no one route may consume the whole process budget. The
  narrowest statement of that is: a route holds at most half of process
  capacity, so a second route always retains at least as much as the busiest
  route holds. Hence `DEFAULT_RESPONSES_MAX_PER_ROUTE =
  DEFAULT_RESPONSES_MAX_CONCURRENCY // 2` (4 at global 8), structurally
  mirroring the established `DEFAULT_RESPONSES_QUEUE_TIMEOUT =
  DEFAULT_UPSTREAM_TIMEOUT`. The contract asserts the invariant, not the
  literal, so retuning the process limit carries the route width with it.
- 2026-08-04: Rejected alternatives, recorded so they are not re-proposed.
  Global divided by the manifest route count couples admission to the provider
  registry, so registering a provider would silently narrow every existing
  route, and it edges toward the per-provider width the spec forbids. Global
  minus one (7) satisfies the saturation scenario arithmetically but abandons
  fairness — one route could hold 7 of 8. Removing the route semaphore entirely
  destroys route attribution in the denial message and the only guard between
  one slow provider and the whole process budget.
- 2026-08-04: A contract constraint bounds the width from above independently of
  fairness. `provider-portable-responses` carries the scenario "One route
  saturates while process capacity remains", which requires a route to saturate
  while the process limit is not binding. If the per-route width equalled the
  global width that scenario would be unobservable, so per-route must stay
  strictly less than global. Half satisfies both bounds at once.

- 2026-08-04: An honest bound, not a bug. `transport/cooldown.remember_failure`
  is called only after an exchange returns, from two sites in
  `transport/exchange.py`. At width `N`, up to `N` same-route requests can
  therefore reach a provider that has just begun rate limiting, instead of
  exactly one. The leak is bounded by the width, closes for every subsequent
  request once the first failure is recorded, is observable as
  `responses_rate_limited`, and is fully reversible by an operator setting
  `CODEX_RESPONSES_PROXY_RESPONSES_MAX_PER_ROUTE=1` in the unit's environment
  and reloading. Exporting it in a shell does not reach a supervised listener.
  This is the risk the `route-slot-lease` chronicle cited when it rejected
  widening; it is accepted here on the owner's report that the upstream no
  longer rate-limits, and it is accepted with a lever rather than silently.
